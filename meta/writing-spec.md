> 适用对象：技术分析类书籍/深度技术文档

## 一、核心原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **准确** | 每个技术论断必须有源码/配置/官方文档依据 | "Nacos 支持 AP 模式" → 应写"通过 `ephemeral=true` 字段选择 Distro 协议实现 AP 模式" |
| **精确** | 类名、方法名、行号、配置 key 必须精确，读者可以据此定位源码 | "配置中心有个长轮询机制" → 应写"`LongPollingService` 类（`config/src/main/java/.../LongPollingService.java:156`）" |
| **深度** | 不只描述"是什么"，要分析"为什么这样设计"、"有哪些 trade-off" | "Nacos 用了 JRaft" → 应分析"为什么选 JRaft 而非原生 Raft？因为 JRaft 的 Pre-Vote 机制防止脑裂" |
| **结构化** | 每小节遵循：问题背景 → 架构设计 → 源码走读 → 设计模式分析 → 小结 | 直接贴一大段代码不解释 |
| **术语统一** | 全文同一个概念用同一个术语，首次出现给出全称 | 一会儿写"服务发现"，一会儿写"服务注册发现" |
| **量化表达** | 技术论断必须有量化数据支撑，禁止使用程度副词 | "延迟大幅降低" → 应写"延迟从 500ms 降至 5ms（降低 99%）" |

### 禁用表达列表（第1-3章经验）

以下表达在技术文档中禁止使用，必须替换为精确量化描述：

| 禁用表达 | 原因 | 替换示例 |
|---------|------|---------|
| "非常"、"特别"、"极其" | 程度副词，无法量化 | "非常快" → "延迟 5ms（P99=15ms）" |
| "很"、"挺"、"比较" | 主观感受词 | "性能很好" → "TPS 达到 15000（+50%）" |
| "有意思"、"有趣" | 主观评价 | 删除或替换为客观特征描述 |
| "强大"、"优秀"、"出色" | 空洞形容词 | "功能强大" → "支持 6 种健康检查类型" |
| "大幅度"、"显著"、"明显" | 无法量化的程度词 | "大幅提升" → "从 10000 TPS 提升到 15000 TPS（+50%）" |
| "优雅"、"巧妙" | 主观审美判断 | 删除或替换为具体设计选择描述 |

### 每节最小源码引用数（第3章教训）

不同类型小节有不同的最低源码引用要求，避免全景类小节写得空洞：

| 小节类型 | 最低源码引用数 | 示例 |
|---------|--------------|------|
| 全景类（模块概览） | ≥ 5 | 3.1 Config 模块全景 |
| 核心类关系图 | ≥ 6 | 3.2 核心类关系图 |
| 源码走读类 | ≥ 8 | 3.3 publishConfig() 走读 |
| 引擎/算法类 | ≥ 5 | 3.7 LongPollingService |
| 持久化/存储类 | ≥ 4 | 3.5 MySQL 持久化 |
| 插件/扩展类 | ≥ 5 | 3.16 配置加密插件 |

### ASCII 图格式兼容规则

ASCII 架构图接受两种格式，质检脚本需同时适配：

1. **注释标记式**：`/* 图 X-Y：描述 */` + ASCII 框线（第1章风格）
2. **直接框线式**：直接使用 ┌┐└┘├┤┬┴┼─│ 等框线字符，无需注释标记（第2-3章风格）

两种格式均视为有效 ASCII 图，不计入字数统计。

## 二、每小节标准结构（6 段式）

```markdown
### X.Y 标题（点明本节核心内容）

**设计背景**（2-3 句）
为什么需要这个机制？解决什么问题？在整体架构中的位置。

**核心类关系图**（ASCII 图）
用 ASCII 图展示关键类之间的调用关系、依赖方向。

**源码走读**（主体，占本节 60%）
按调用链顺序逐个方法走读：
1. 入口方法（给出类名.方法名 + 文件路径）
2. 核心逻辑（引用关键源码片段，带行号）
3. 分支逻辑处理
4. 返回结果

**设计模式分析**（3-5 句）
识别源码中使用的设计模式（模板方法/策略/观察者/装饰器等），分析为什么此处用这个模式。

**小结**（1-2 句）
本节核心要点一句话总结。
```

## 三、源码引用格式规范

```java
// ✅ 正确引用格式：
// ClientWorker.java (client/src/main/java/.../ClientWorker.java:156-172)
public void checkServerConfig() {
    // 1. 收集所有需要监听的配置
    List<CacheData> cacheDatas = new ArrayList<>(cacheMap.get().values());
    // 2. 按 namespace 聚合，逐个发起长轮询
    Map<String, List<CacheData>> grouped = groupByTenant(cacheDatas);
    ...
}
```

关键要求：
- **必须带文件路径 + 行号**，读者可以定位到源码
- **只引用关键逻辑**，不要整段贴
- **引用后必须有分析**，不能贴完代码就走

## 四、语言风格要求

| 维度 | 要求 | 示例 |
|------|------|------|
| **人称** | 避免"我们""你"，用被动或中性描述 | "Nacos 采用 Distro 协议实现..." ✅ / "我们可以看到 Nacos 用了..." ❌ |
| **时态** | 一般现在时 | "该方法调用 `syncToTargetServerAsync()` 进行异步同步" |
| **修饰** | 避免"非常""十分""极其"等主观副词 | "性能显著提升" ❌ → "TPS 从 10000/s 提升到 15000/s" ✅ |
| **类比** | 避免尴尬类比，用技术对比 | "就像快递员送包裹一样" ❌ → "异步消息队列采用生产者-消费者模式" ✅ |
| **缩写** | 首次出现给出全称 | "Raft 共识算法（以下简称 Raft）" |

## 六、常见写作错误与修正

| 错误类型 | 错误示例 | 修正 |
|---------|---------|------|
| 空洞描述 | "Nacos 的配置中心功能很强大" | "Nacos Config 模块支持配置发布、长轮询变更通知、历史版本回滚、Beta 灰度发布等 6 项核心能力" |
| 无依据断言 | "这种设计性能最好" | "该设计采用异步非阻塞 I/O，相比同步阻塞模型，在 1000 并发下延迟降低 60%（基准测试数据见 11.14 节）" |
| 概念混淆 | "服务注册到 Nacos" | "服务实例注册到 Nacos Naming 模块" |
| 源码引用缺失 | "ClientWorker 会定期检查配置" | "`ClientWorker.checkServerConfig()` 方法（`client/src/.../ClientWorker.java:156`）每 10ms 执行一次长轮询检查" |
| 口语化表达 | "这个功能挺有意思的" | "该设计通过事件驱动机制实现了模块间解耦" |

## 零、写作前置检查（第3章教训）

**⛔ 必须在开始每章写作前完成以下检查，禁止边写边发现差异：**

| # | 检查项 | 说明 |
|---|--------|------|
| 0.1 | **大纲 2.5.3 验证** | 逐小节检查大纲中的类名、方法名、模块路径是否在 2.5.3 源码中存在 |
| 0.2 | **废弃类识别** | 对照 2.2.3→2.5.3 差异表，标记大纲中已废弃/重命名的类 |
| 0.3 | **模块结构验证** | 确认模块拆分/合并（如 persistence 独立模块、Config 模块瘦身） |
| 0.4 | **新增大纲小节** | 若修订大纲新增小节，必须在对应章节中实际写入内容，避免大纲-内容不一致 |

### 0.5 子Agent协作规则

使用子Agent并行写作时，必须遵守以下规则：

1. **严格遵守大纲小节编号**：子Agent不得自创小节编号，必须严格按大纲给定的编号写入
2. **小节编号唯一性**：主Agent在写入新小节前，必须先检查目标编号是否已被子Agent占用
3. **合并时检查冲突**：多个子Agent产出合并时，必须检查是否存在同编号小节冲突
