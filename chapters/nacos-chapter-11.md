## 11.1 CAP 理论在 Nacos 中的实践：AP vs CP 属性对比表

### 设计背景

分布式系统的 CAP 定理（Brewer's Theorem, 2000 年由 Eric Brewer 提出，2002 年由 Gilbert & Lynch 形式化证明）指出：一个分布式系统在**分区容错性（Partition Tolerance）**必然存在的前提下，只能在**一致性（Consistency）**和**可用性（Availability）**之间二选一——不可能三者同时满足。

Nacos 作为面向微服务生态的注册中心 + 配置中心双重基础设施，需要同时支撑两类不同需求：

1. **微服务注册发现（Naming）**：微服务实例频繁上下线（心跳间隔 5s），对可用性要求极高——宁可返回稍旧的服务列表，也不能因追求强一致性而拒绝服务发现请求
2. **配置管理（Config）**：配置变更需要确保所有节点最终一致，发布配置后不能出现"部分节点返回旧配置、部分节点返回新配置"的读取不一致

Nacos 2.5.3 的核心设计原则是：**在同一个集群中同时提供 AP 和 CP 两种模式**——Naming 模块使用自研的 Distro 协议实现 AP，Config 模块使用 JRaft 协议实现 CP。这在同类注册中心中是独特的"AP+CP 混合模式"架构。

### CAP 属性在 Nacos 中的映射矩阵

| CAP 属性 | 定义 | Nacos 实现 | 对应模块 | 协议 |
|---------|------|-----------|---------|------|
| **C** (Consistency) | 所有节点在同一时刻看到相同数据 | Config 模块：JRaft Leader 提交日志后，Follower 同步确认 | Config | JRaft |
| **A** (Availability) | 每个请求都能获得非错误的响应 | Naming 模块：所有节点独立接收注册请求，返回服务列表（可能稍旧） | Naming | Distro |
| **P** (Partition Tolerance) | 系统在网络分区下仍能继续工作 | 两个模块均支持：Distro 异步同步 + JRaft 多数派选举 | Naming + Config | Distro + JRaft |

### Distro 协议（AP 模式）核心机制

Nacos 自研的 Distro 协议是专为服务发现场景设计的 AP 协议。其核心设计思路：

**1. 全节点平等写入**

与 JRaft 的 Leader 单点写入不同，Distro 允许每个 Nacos 节点独立接受客户端的服务注册请求。当一个节点接收到注册请求时：

```
client → Nacos Node1: register(serviceA, 192.168.1.1:8080)
                │
                ├── 1. 本地写入内存注册表 (立即返回成功)
                │
                └── 2. 异步同步到其他节点 (Distro 同步任务)
                     ├── Node1 → Node2: sync(serviceA, 192.168.1.1:8080)
                     └── Node1 → Node3: sync(serviceA, 192.168.1.1:8080)
```

源码位置：`naming/src/main/java/com/alibaba/nacos/naming/cluster/transport/` 下的 Distro 数据传输层。

**2. 最终一致性模型**

Distro 不保证写入后立即全局一致，而是通过异步同步任务在后台逐渐将数据扩散到集群所有节点。每个节点维护一个本地的 `DataStore`（服务注册表），通过周期性 Checksum 校验对比与其他节点的数据差异，触发差异同步。

**3. 健康检查与自动剔除**

Distro 内置健康检查机制——每个节点对本地注册的服务实例定期发送心跳探测，心跳超时的实例被自动标记为不健康（`healthy=false`），并通过 Distro 同步任务将此状态扩散到其他节点。确保最终所有节点一致地剔除不健康实例。

### JRaft 协议（CP 模式）核心机制

JRaft 是阿里巴巴基于 Raft 论文实现的开源 Java Raft 库。Nacos 2.5.3 采用 JRaft 作为 Config 模块的一致性协议。核心流程：

**1. Leader 单点写入**

```
Client → Nacos Node1 (Leader):
  publishConfig(dataId, group, content)
    │
    ├── 1. Leader 先写入本地日志 (Raft Log Entry)
    │
    ├── 2. Leader 向所有 Follower 发送 AppendEntries RPC
    │       ├── Follower1: 接收日志条目 → 写入本地日志 → 返回 ACK
    │       └── Follower2: 接收日志条目 → 写入本地日志 → 返回 ACK
    │
    ├── 3. Leader 收到多数派 ACK (≥ 2/3) → 提交日志
    │
    └── 4. Leader 返回客户端成功
```

源码位置：`consistency/src/main/java/com/alibaba/nacos/consistency/cp/JRaftProtocol.java`

**2. 强一致性保证**

JRaft 确保已提交的日志条目在所有存活节点上最终一致——新 Leader 被选举后，其他 Follower 的未提交日志将被新 Leader 覆盖（以 Leader 日志为准）。这保证了：

- 已提交的日志永远不会丢失（已写入多数派节点）
- 未提交的日志可能在 Leader 切换时丢失（客户端需要重试）

### AP vs CP 对比矩阵

| 维度 | Distro (AP) | JRaft (CP) |
|------|-------------|------------|
| **一致性模型** | 最终一致性 | 强一致性 |
| **写入方式** | 全节点独立写入 | Leader 单点写入 |
| **写入延迟** | 极低（本地写入即返回） | 较高（等待多数派确认） |
| **冲突处理** | 最后写入覆盖（Last-Write-Wins） | Leader 串行化写入，无冲突 |
| **节点故障容忍** | 允许少数节点不可用 | 多数派存活即可 |
| **适用场景** | 服务注册发现（高频写入） | 配置发布（低频写入） |
| **数据一致性窗口** | 秒级（异步同步延迟） | 实时（提交即一致） |
| **读取一致性** | 可能读到旧数据 | 读取 Leader 保证最新 |
| **Nacos 模块** | Naming | Config |
| **Nacos 版本** | 自研（Nacos 1.0+） | 基于 JRaft（Nacos 2.0+） |

### 为什么 Nacos 不统一用 JRaft（CP）？

这是 Nacos 架构设计的核心 Trade-off：如果 Naming 模块也用 JRaft（CP 模式），会带来以下问题：

**1. 写入高延迟不可接受**

微服务实例注册是高频操作（大规模集群每秒数千次注册请求）。JRaft 的 Leader 单点写入 + 多数派确认机制，每个注册请求需要跨网络 RTT × 2（Leader → Follower → ACK）。对于心跳间隔 5s 的微服务来说，过高的注册延迟可能导致心跳超时误判实例下线。

Distro 本地写入即返回，写入延迟极低（< 1ms），适合高频注册场景。

**2. Leader 节点压力集中**

如果所有注册请求都路由到 Leader 节点，Leader 的 CPU 和网络带宽将成为集群瓶颈。Distro 的全节点独立写入将写入压力均匀分散到所有节点。

**3. CP 模式下的可用性牺牲**

当集群发生网络分区时，JRaft 的少数派节点（被孤立的节点）无法接受写入——这对服务注册场景是致命问题：被孤立的 Nacos 节点对应的微服务无法注册。Distro 允许每个节点独立接受注册，即使发生网络分区，每个分区内的 Nacos 节点仍可接受注册——只是分区恢复后通过异步同步合并数据。

### Trade-off 分析

**AP+CP 混合 vs 统一 CP 模式**：

| 维度 | AP+CP 混合（Nacos 实际设计） | 统一 CP（假设设计） |
|------|--------------------------|-------------------|
| Naming 写入延迟 | < 1ms（本地写入） | ~10-50ms（Leader RPC） |
| Naming 可用性 | 网络分区仍可用 | 少数派节点不可写入 |
| Config 一致性 | 强一致（JRaft） | 强一致（相同） |
| 架构复杂度 | 两套协议共存维护成本高 | 单一协议统一维护 |
| 客户端复杂度 | 需感知 AP/CP 选择 | 统一客户端逻辑 |

**Distro 异步同步延迟的影响**：

Distro 的最终一致性窗口（通常 < 1s）在高频心跳场景下影响可忽略——即使短暂时间窗口内不同 Nacos 节点返回的服务列表有微秒差异，客户端的本地缓存（`ServiceInfo` + `CacheData`）可平滑覆盖此窗口。

### 设计模式分析

1. **策略模式（Strategy）**：Nacos 在 Naming 和 Config 两个模块中解耦了AP/CP 策略——客户端通过 `ephemeral=true/false` 选择 AP/Distro（临时实例）或 CP/JRaft（持久实例）。同一个 Nacos 集群承载两种一致性策略，通过客户端属性字段切换。

2. **代理模式（Proxy）**：一致性协议层（Distro / JRaft）作为 Naming/Config 模块的数据同步代理——上层模块不感知底层协议切换，通过抽象一致性层 CP/AP 接口统一为上层提供数据同步能力。

3. **观察者模式（Observer）**：Distro 的异步同步任务 + Checksum 校验机制——各节点定期相互 Checksum 对比发现数据差异，触发差异同步任务。类似 ZooKeeper 的 Watcher 机制但非实时触发（周期性主动 Pull）。

### 小结

- Nacos 2.5.3 采用独特的 AP+CP 混合模式：Naming 模块用 Distro（AP，最终一致性），Config 模块用 JRaft（CP，强一致性）
- Distro 全节点独立写入 + 异步同步，延迟 < 1ms，适合高频服务注册；JRaft Leader 单点写入 + 多数派确认，延迟 ~10-50ms，适合低频配置发布
- Naming 选 AP 而非 CP 的核心原因：高写入频率（数万注册/秒）、网络分区仍需可用、Leader 压力分散
- Distro 最终一致性窗口（< 1s）对客户端影响可忽略——客户端本地缓存平滑覆盖差异窗口

## 11.2 AP vs CP 模式选择决策树（需要持久化？→CP / 高频心跳？→AP）

### 设计背景

Nacos 客户端在注册服务实例时需要明确指定实例类型：**临时实例（ephemeral=true）** 使用 AP/Distro 协议，**持久实例（ephemeral=false）** 使用 CP/JRaft 协议。这个选择直接影响实例的健康检查机制、数据一致性保证和故障恢复行为。

然而，开发者在实际业务中经常困惑："我的微服务应该注册为临时实例还是持久实例？"——这需要业务场景对一致性、可用性和持久化需求进行决策。Nacos 2.5.3 没有提供自动推荐，因此需要一个系统化的决策框架。

本节提出一个三层决策树模型，帮助开发者根据业务需求在 AP（临时实例）和 CP（持久实例）之间做出明确选择。

### 三层决策逻辑详解

#### Q1：服务实例宕机后是否需要自动恢复？

这是最关键的第一层决策。Nacos 对临时实例和持久实例的故障处理策略截然不同：

| 行为 | 临时实例 (AP) | 持久实例 (CP) |
|------|-------------|-------------|
| **心跳机制** | 客户端主动发送心跳（默认 5s） | Nacos 服务端主动健康检查 |
| **心跳超时** | 15s 无心跳 → 自动剔除 | 不剔除，标记为 UNHEALTHY |
| **客户端宕机** | 自动从服务列表移除 | 保留在服务列表（状态=UNHEALTHY） |
| **客户端恢复** | 重新注册（新实例 ID） | 健康检查恢复 → 状态恢复 HEALTHY |
| **持久化** | 仅内存（不写入 MySQL） | 写入 MySQL（JRaft 日志持久化） |

**决策规则**：
- **不需要自动恢复** → 选 AP（临时实例）。例如：K8s Pod 宕机后 K8s 自动重启新 Pod，新 Pod 以新 IP 重新注册——旧实例自动剔除正好符合
- **需要保持实例列表稳定** → 选 CP（持久实例）。例如：DNS 服务器 IP 列表、数据库主从节点列表——即使节点暂时不可达也不应剔除

#### Q2（仅 CP 分支）：心跳频率多高？

持久实例的健康检查间隔由  控制（默认 5s）。心跳频率影响健康检查开销：

- **> 10s**：低频健康检查，适合基础设施服务（DNS/IP 列表），允许较长故障检测延迟
- **5-10s**：标准健康检查，适合大多数持久实例
- **< 5s**：高频健康检查，适合关键业务服务（数据库主从节点），需要快速感知故障

#### Q3（高频心跳分支）：是否需要保持实例列表稳定？

即使心跳频率高、需要快速感知故障，如果业务逻辑依赖实例列表稳定（例如负载均衡算法基于固定 IP 列表），仍应选 CP——避免实例被自动剔除导致负载均衡策略失效。

### 典型场景决策速查表

| 业务场景 | Q1:自动恢复？ | Q2:心跳频率 | Q3:保持列表？ | 推荐模式 | 原因 |
|---------|:---:|:---:|:---:|:---:|------|
| K8s Pod 微服务 | 不需要 | - | - | **AP** | Pod 重启自动注册新 IP |
| Spring Boot 微服务 | 不需要 | - | - | **AP** | 进程重启新实例自动注册 |
| DNS 服务器列表 | 需要 | > 10s | 是 | **CP** | 即使 DNS 服务器暂时不可达也不应剔除 |
| MySQL 主从节点 | 需要 | < 5s | 是 | **CP** | 快速感知主从切换 |
| Kafka Broker 列表 | 需要 | 5-10s | 是 | **CP** | Broker 宕机需手动恢复 |
| API 网关实例 | 不需要 | - | - | **AP** | 网关自动扩缩容 |
| Redis 哨兵节点 | 需要 | < 5s | 是 | **CP** | 哨兵节点变更需即时感知 |
| 定时任务调度器 | 需要 | 5-10s | 否 | **AP** | 调度器实例上下线频繁 |

### Trade-off 分析

**AP vs CP 的适用边界**：

| 考量维度 | AP (临时实例) | CP (持久实例) |
|---------|-------------|-------------|
| **适用实例数量** | 数十~数万（高频注册） | 数十~数百（低频注册） |

**临时实例的集群重启风险**：

Nacos 集群全部重启后，所有节点内存清空——**所有临时实例注册信息全部丢失**。客户端需要重新发送注册请求。大规模集群重启后可能出现"注册风暴"——数千个客户端同时重新注册，瞬时写入压力可能击垮 Nacos。缓解措施：(a) 客户端注册添加随机延迟（0-5s）；(b) 分批重启 Nacos 节点

### 设计模式分析

1. **决策树模式（Decision Tree）**：AP vs CP 选择构建为三层决策树——每层一个问题逐步缩小决策空间，最终叶子节点指向推荐模式。避免开发者需要同时考虑所有因素
2. **策略模式（Strategy）**：客户端通过  字段切换 AP/CP 策略——业务需求变化时只需修改一个布尔字段，无需改动代码逻辑

### 小结

- AP（临时实例，）：客户端心跳保活，宕机自动剔除，适合无状态微服务（K8s Pod/Spring Boot）
- CP（持久实例，）：服务端健康检查，宕机不自动剔除，适合基础设施服务（DNS/数据库节点列表）
- 三层决策树：Q1 是否需要自动恢复？→ Q2 心跳频率？→ Q3 保持列表稳定？逐层缩小决策空间
- 临时实例集群全部重启后全部丢失——需客户端重新注册，大规模重启可能引发注册风暴

## 11.3 集群脑裂场景分析：网络分区导致双 Leader 的完整时序图

### 设计背景

Raft 共识算法依赖 Leader 节点协调所有写入操作。在正常情况下，集群中只有一个 Leader，所有 Follower 接收 Leader 的日志复制。但当集群发生**网络分区（Network Partition）**时——部分节点之间的网络中断，导致集群分裂为两个或多个互不相通的子集群——可能触发最危险的场景：**双 Leader（Split-Brain）**。

Nacos 2.5.3 集群基于 JRaft 协议，网络分区导致双 Leader 的典型场景如下：

1. 初始状态：5 节点集群（Node1=Leader, Node2-5=Follower）
2. 网络分区：Node1-2 与 Node3-5 之间网络中断
3. Node1-2 分区（2 节点）：Node1 仍认为自己是 Leader，但无法收到 Node3-5 的心跳响应
4. Node3-5 分区（3 节点）：Node3-5 检测到 Leader 心跳超时 → 触发新 Leader 选举 → Node3 当选为新 Leader
5. **双 Leader 并存**：分区 A 有 Leader Node1，分区 B 有 Leader Node3——两个 Leader 同时接受客户端写入

双 Leader 是最危险的分布式故障场景——两个 Leader 各自接受写入，导致数据永久不一致（即使网络恢复后也无法自动合并冲突写入）。

### 双 Leader 的关键触发条件

Raft 协议的双 Leader 场景需要**同时满足**以下条件：

**1. 网络分区恰好将集群分为两个都能形成多数派的子集群**

这是最危险的网络分区模式。对于 5 节点集群：

| 分区模式 | 分区 A | 分区 B | 能否形成双 Leader？ | 原因 |
|---------|--------|--------|:---:|------|
| 1-4 分裂 | 1 节点 | 4 节点 | ❌ | 分区 A (1 节点) 无法选举出新 Leader（未达多数派 3/5） |
| 2-3 分裂 | 2 节点 | 3 节点 | ✅ | 分区 B (3 节点) 可选举新 Leader（达到多数派 3/5），分区 A 的旧 Leader 认为自己是 Leader（2 节点但无法确认） |
| 2-2-1 分裂 | 2 节点 | 2 节点 | ❌ | 两个分区均无法选举出新 Leader（均未达多数派 3/5） |

**2. 旧 Leader 恰好在少数派分区**

如果网络分区后，少数派分区（2 节点）恰好包含旧 Leader——旧 Leader 无法感知自己已失去多数派支持（因为无法收到多数派的心跳响应），继续认为自己是 Leader。而此时多数派分区（3 节点）已选举出新 Leader。

**3. 选举超时差异**

如果少数派分区的 Follower 节点恰好先触发选举超时（在收到新 Leader 心跳之前），也可能在少数派分区内选举出另一个 Leader——但这种情况下新 Leader 无法获得多数派投票（只有 2/5 投票），选举失败。

### JRaft 的 Pre-Vote 机制如何阻止双 Leader？

JRaft 实现了 Raft 论文中提出的 **Pre-Vote（预投票）** 机制，专门防止网络分区后的无效选举。Pre-Vote 的核心思想：**在正式发起 RequestVote RPC 之前，先发起 Pre-Vote RPC 试探其他节点是否愿意投票**。

Pre-Vote 的 3 层检查：

**第 1 层：Term 检查**
Candidate 发起 Pre-Vote RPC，携带自己的 `lastLogTerm` 和 `lastLogIndex`。接收方检查 Candidate 的日志是否至少和自己一样新（`lastLogTerm > myLastLogTerm` 或 `lastLogTerm == myLastLogTerm && lastLogIndex >= myLastLogIndex`）。

**第 2 层：Leader 存活检查**
接收方在最近 `Election Timeout` 时间内是否收到过 Leader 的心跳？如果收到过——说明 Leader 仍存活，拒绝 Pre-Vote。

**第 3 层：日志最新检查**
接收方的日志是否比 Candidate 的日志更新？如果是——拒绝 Pre-Vote（ Candidate 日志落后，不应该成为 Leader）。

三层检查通过后，Candidate 才正式发起 RequestVote RPC。Pre-Vote 机制在网络分区场景下阻止双 Leader 的过程：

```
分区 A (Node1-2, 含旧 Leader Node1)        分区 B (Node3-5)
─────────────────────────────────────────────────────────────────────

Node1 (Leader):                           Node3 (Follower):
  │                                          │
  │  ← 网络中断 →                            │
  │                                          │
  │                                          ├── 选举超时 (150ms)
  │                                          │
  │                                          ├── Pre-Vote RPC → Node4
  │                                          │   Q: 愿意投票给我吗？
  │                                          │   Node4 检查:
  │                                          │   Layer 1 (Term): ✅ Node3.term > mine
  │                                          │   Layer 2 (Leader存活): ✅ 150ms 内
  │                                          │       未收到 Leader 心跳
  │                                          │   Layer 3 (日志最新): ✅ Node3 日志
  │                                          │       不比我的旧
  │                                          │   → Pre-Vote GRANTED ✅
  │                                          │
  │                                          ├── Pre-Vote RPC → Node5
  │                                          │   → Pre-Vote GRANTED ✅
  │                                          │
  │                                          ├── 获得多数派 Pre-Vote (2/3)
  │                                          │
  │                                          ├── 正式 RequestVote RPC → Node4,5
  │                                          │   → 当选为新 Leader (Term=N+1)
  │                                          │
  │  ← 网络恢复 →                            │
  │                                          │
  ├── 收到 Node3 的 AppendEntries RPC         │
  │   (Term=N+1 > 自己的 Term=N)              │
  │   → Step Down (退位为 Follower)          │
  │   → 覆盖未提交日志                     │
```

如果没有 Pre-Vote 机制，Node3 在网络分区后直接发起 RequestVote RPC——即使成功当选为新 Leader（获得多数派投票），旧 Leader Node1 在分区 A 中仍认为自己是 Leader（因为在分区 A 中 Node1 仍能收到 Node2 的心跳响应）——导致双 Leader 持续时间更长（直到网络恢复）。

**Pre-Vote 的实际效果**：即使网络分区导致双 Leader，Pre-Vote 确保新 Leader 的 Term 更高——网络恢复后旧 Leader 发现新 Leader 的 Term > 自己的 Term → 自动退位 → 双 Leader 自动收敛为单 Leader。**Pre-Vote 不能完全阻止双 Leader，但确保双 Leader 在网络恢复后立即自动收敛**。

### Trade-off 分析

**Pre-Vote vs 无 Pre-Vote**：

| 维度 | 有 Pre-Vote (JRaft 实际) | 无 Pre-Vote (标准 Raft) |
|------|--------------------------|------------------------|
| 无效选举次数 | 少（Pre-Vote 过滤无效 Candidate） | 多（可能多次无效选举） |
| 双 Leader 收敛速度 | 网络恢复后立即收敛 | 取决于旧 Leader 何时发现新 Leader |
| 选举延迟 | 增加 1 RTT（Pre-Vote RPC 往返） | 无额外延迟 |
| 网络分区恢复后行为 | 旧 Leader 自动退位 | 旧 Leader 可能继续保持 Leader（直到收到新 Leader 心跳） |

**3 节点 vs 5 节点集群的脑裂风险**：

| 维度 | 3 节点 | 5 节点 |
|------|--------|--------|
| 可能出现双 Leader 的网络分区模式 | 无（任何分裂均无法产生两个多数派分区） | 2-3 分裂可能产生双 Leader |
| 最小双 Leader 分区节点数 | N/A | 分区 A: 2 节点（含旧 Leader），分区 B: 3 节点 |
| 双 Leader 自动收敛时间 | N/A | 网络恢复后 < 10ms（旧 Leader 收到新 Leader 心跳） |

### 设计模式分析

1. **预投票模式（Pre-Vote Pattern）**：Pre-Vote 在正式投票前增加预筛选阶段——避免无效 Candidate 发起正式选举，减少集群震荡。类似两阶段提交（2PC）的思想：先询问"是否愿意投票"（Pre-Vote），再正式发起投票（RequestVote）

2. **Term 单调递增模式（Monotonic Term）**：Raft 的 Term 全局单调递增——任何节点发现 Term > 自己的 Term → 立即退位转为 Follower。这是 Raft 协议最简洁但最核心的安全机制：无论集群处于何种分裂状态，最高的 Term 最终会"征服"所有节点

### 小结

- 5 节点集群在 2-3 网络分裂模式下可能出现双 Leader：分区 A (2 节点含旧 Leader) + 分区 B (3 节点选新 Leader)
- 双 Leader 场景需同时满足：网络分区恰好产生两个多数派分区 + 旧 Leader 恰好在少数派分区
- JRaft 的 Pre-Vote 机制通过 3 层检查（Term / Leader 存活 / 日志最新）过滤无效 Candidate，减少无效选举
- Pre-Vote 不能完全阻止双 Leader，但确保网络恢复后旧 Leader 自动退位（Term 单调递增强制收敛）
- 3 节点集群天然免疫双 Leader——任何分裂均无法产生两个多数派分区（每个分区最多 1-2 节点，均 < 2/3 quorum）

## 11.4 Raft Pre-Vote 防脑裂机制：3 层检查（term / Leader 存活 / 日志最新）

### 设计背景

Raft 协议的标准 Leader 选举流程中，Follower 在选举超时（Election Timeout）后直接转为 Candidate 状态，增加自己的 CurrentTerm，给自己投票，然后向所有其他节点发送 RequestVote RPC。这个流程在正常情况下工作良好——但在网络分区场景下可能产生严重问题：

**问题场景**：一个网络分区的少数派节点（无法获得多数派投票）反复超时 → 反复转为 Candidate → 反复增加 Term → 反复发起选举。即使每次选举都失败（无法获得多数派投票），Term 仍在不断递增。当网络恢复后，这个少数派节点带着极高的 Term 重新加入集群——迫使集群中的合法 Leader 退位（因为 Term 落后），触发不必要的 Leader 切换。

**Pre-Vote 的核心思想**：在正式增加 Term 和发起 RequestVote RPC 之前，先发起一轮 Pre-Vote RPC 试探其他节点是否愿意投票。只有获得多数派 Pre-Vote 同意后，才正式增加 Term 和发起 RequestVote。这避免了上述"少数派节点反复增加 Term"的问题——因为在网络分区中，少数派节点的 Pre-Vote 无法获得多数派同意，因此永远不会进入正式选举流程。

JRaft 实现了完整的 Pre-Vote 机制（参考 Raft 论文第 9.6 节），通过 3 层检查确保 Pre-Vote 的安全性。

### 核心流程图

```
┌──────────────────────────────────────────────────────────────────────────────┐
│              JRaft Pre-Vote 3 层检查完整流程                              │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  Follower (选举超时 150ms)                                              │
│       │                                                                  │
│       ├── 1. 不立即增加 Term！先进入 Pre-Candidate 状态                  │
│       │                                                                  │
│       ├── 2. 向所有节点发送 Pre-Vote RPC                               │
│       │    (lastLogTerm, lastLogIndex)                                   │
│       │                                                                  │
│       ▼                                                                  │
```

### 3 层检查逐一详解

#### Layer 1：Term 检查——"你的日志比我旧吗？"

这是最基本的日志新鲜度检查。Raft 协议要求 Leader 必须拥有集群中最新的日志——否则已提交的日志可能被新 Leader 覆盖。

检查逻辑（JRaft `NodeImpl.java` 中的 `handlePreVoteRequest` 方法）：

```
if (Candidate.lastLogTerm < myLastLogTerm) {
    → REJECT: Candidate 的日志 Term 落后于我的日志 Term
}

if (Candidate.lastLogTerm == myLastLogTerm &&
    Candidate.lastLogIndex < myLastLogIndex) {
    → REJECT: Candidate 的日志 Index 落后于我（同 Term 下日志更短）
}
```

**为什么这一层检查很重要？**

假设 Node3 因网络分区被隔离，其日志落后于集群中的多数派节点。如果 Node3 可以成为 Leader，它将用落后日志覆盖集群中已提交的日志——这是 Raft 协议绝对要避免的。

#### Layer 2：Leader 存活检查——"Leader 还活着吗？"

这是 Pre-Vote 特有的检查——防止在 Leader 存活时触发无效选举。

检查逻辑：

```
if (timeSinceLastHeartbeat < ElectionTimeout) {
    → REJECT: 我在最近 ElectionTimeout 时间内收到过 Leader 的心跳
}
```

**为什么这一层很重要？**

假设 Follower 因为 GC 停顿导致选举超时——但实际上 Leader 仍存活并正常发送心跳。如果没有这一层检查，Follower 会发起 Pre-Vote → 获得多数派同意 → 正式选举新 Leader → 不必要的 Leader 切换（旧 Leader 退位 → 新 Leader 当选 → 集群震荡）。

这一层检查等价于："Leader 还活着吗？如果还活着，不要发起选举。"

#### Layer 3：日志最新检查——"我的日志比 Candidate 更新吗？"

这是 Layer 1 的反向检查——接收方的日志比 Candidate 的日志更新。

检查逻辑：

```
if (myLastLogTerm > Candidate.lastLogTerm) {
    → REJECT: 我的日志 Term 比 Candidate 更高 → 我更适合成为 Leader
}

if (myLastLogTerm == Candidate.lastLogTerm &&
    myLastLogIndex > Candidate.lastLogIndex) {
    → REJECT: 同 Term 下我的日志更长 → 我更适合成为 Leader
}
```

**为什么这一层很重要？**

这一层确保 Candidate 的日志至少不比接收方差——如果接收方自己的日志更新，说明 Candidate 不适合成为 Leader（因为它需要从接收方同步落后日志，效率更低）。

### Pre-Vote 的安全性保证

Pre-Vote 机制的安全性由以下不变量保证：

**不变量 1：Term 只在获得多数派 Pre-Vote 后才增加**

这意味着在网络分区中，少数派节点无法增加 Term（因为 Pre-Vote 无法获得多数派同意）。这避免了"少数派节点反复增加 Term → 网络恢复后迫使合法 Leader 退位"的问题。

**不变量 2：Pre-Vote 通过的 Candidate 在正式选举中必定获得多数派投票**

因为 Pre-Vote 的 3 层检查比正式 RequestVote 更严格（Layer 2: Leader 存活检查仅在 Pre-Vote 中存在），因此 Pre-Vote 通过意味着正式 RequestVote 也会通过。

**不变量 3：任何已提交的日志不会被新 Leader 覆盖**

Layer 1 和 Layer 3 的日志新鲜度检查确保新 Leader 的日志至少包含所有已提交的日志——这是 Raft 协议的安全性的核心保证。

### Pre-Vote vs 标准 Raft 选举对比

| 维度 | 标准 Raft (无 Pre-Vote) | JRaft (有 Pre-Vote) |
|------|------------------------|----------------------|
| 网络分区中少数派节点行为 | 反复增加 Term + 反复选举失败 | 停留在 Follower 状态（Pre-Vote 无法通过） |
| 网络恢复后 Term | 少数派节点 Term 极高 → 迫使合法 Leader 退位 | 少数派节点 Term 未增加 → Leader 不受影响 |
| 不必要的 Leader 切换 | 可能发生（如上） | 不会发生（少数派 Term 未增加） |
| GC 停顿导致的选举 | 正常选举新 Leader → 旧 Leader 退位 | Layer 2 阻止：Leader 存活 → Pre-Vote REJECT |
| 选举延迟 | 1 RTT（RequestVote RPC） | 2 RTT（Pre-Vote RPC + RequestVote RPC） |

### Trade-off 分析

**Pre-Vote 的代价：增加 1 RTT 选举延迟**

Pre-Vote 在正式选举前增加了 1 轮 RPC（Pre-Vote RPC 往返），导致选举延迟从 1 RTT 增加到 2 RTT。对于 Nacos 集群（同机房 RTT < 1ms），这 1 RTT 的增加可忽略（+1ms）。但对于跨地域集群（RTT ~30ms），选举延迟从 ~30ms 增加到 ~60ms。

**权衡**：牺牲 1 RTT 选举延迟 → 避免网络分区 + GC 停顿场景下的 Term 无限制递增和不必要的 Leader 切换。这是一个明显值得的 trade-off——1 RTT 延迟 vs 集群稳定性。

### 设计模式分析

1. **两阶段提交模式（2PC）**：Pre-Vote + RequestVote 构成两阶段提交——Phase 1（Pre-Vote）：询问是否愿意投票（试探阶段）；Phase 2（RequestVote）：正式投票（提交阶段）。只有 Phase 1 多数派通过才进入 Phase 2——避免无效的 Phase 2（正式投票失败导致 Term 无意义递增）

2. **门卫模式（Guard Pattern）**：3 层检查构成 Leader 选举的门卫——Candidate 必须通过全部 3 层检查（日志新鲜度 / Leader 存活 / 日志最新）才能进入正式选举。每一层是一个门卫，过滤不符合条件的 Candidate

### 小结

- JRaft Pre-Vote 在正式 RequestVote 前增加 Pre-Vote RPC 阶段，通过 3 层检查（Term / Leader 存活 / 日志最新）过滤无效 Candidate
- Layer elta2 (Leader 存活检查) 是 Pre-Vote 特有的——防止 Leader 存活时的无效选举（GC 停顿导致的选举超时）
- Pre-Vote 的核心价值：防止网络分区中少数派节点反复增加 Term → 网络恢复后迫使合法 Leader 退位
- Pre-Vote 不能完全阻止双 Leader，但确保：(a) 网络分区中少数派节点 Term 不增加 (b) 网络恢复后双 Leader 自动收敛
- Pre-Vote 代价：增加 1 RTT 选举延迟（同机房 < 1ms，跨地域 ~30ms）——换取集群稳定性

## 11.5 脑裂恢复 3 阶段策略：检测→仲裁→数据合并

### 设计背景

当 Nacos 集群经历网络分区并出现双 Leader（参见 11.3 节）后，网络恢复时集群面临以下恢复挑战：

1. **旧 Leader 退位**：少数派分区的旧 Leader（Term 较低）必须自动退位，接受新 Leader（Term 较高）的日志覆盖
2. **未提交日志丢失**：旧 Leader 在分区期间接受的写入（未获得多数派确认，未提交）将在退位时被覆盖——客户端需要重试这些写入
3. **数据不一致窗口**：分区期间两个 Leader 各自接受写入——网络恢复后其中一个 Leader 的未提交日志丢失

Nacos 2.5.3 基于 JRaft 的脑裂恢复不依赖人工干预——完全自动化。恢复过程分为 3 个阶段：**检测（Detection）→ 仲裁（Arbitration）→ 数据合并（Data Reconciliation）**。

### 阶段 1：检测（Detection）

检测阶段由 Raft 协议的 **Term 单调递增**机制自动触发——网络恢复后，旧 Leader 收到新 Leader 的心跳/AppendEntries RPC，发现对方 Term > 自己的 Term → 立即 Step Down。

**关键代码逻辑（JRaft NodeImpl.java）**：

```java
// JRaft NodeImpl.handleAppendEntriesRequest
if (request.getTerm() > this.currTerm) {
    // 发现对方 Term > 自己的 Term → 立即退位
    stepDown(request.getTerm());
    // 转为 Follower 状态
    // 停止接受客户端写入
    // 清空 pendingCommitIndex
}
```

**检测阶段的耗时**：取决于网络恢复后旧 Leader 多快收到新 Leader 的心跳。JRaft 默认心跳间隔 500ms——因此最坏情况下检测耗时 < 500ms（上一次心跳刚过后网络恢复 → 等待下一个心跳周期）。

### 阶段 2：仲裁（Log Arbitration）

仲裁阶段由 Leader 向所有 Follower 发送 AppendEntries RPC 触发。核心规则：**以 Leader 日志为准——Leader.Term > Follower.Term → Leader 的日志版本覆盖 Follower 的日志版本**。

**日志冲突仲裁算法**：

```
Leader 向 Follower 发送 AppendEntries RPC:
  prevLogIndex = Follower 已同步的最新日志 Index
  prevLogTerm = prevLogIndex 处日志的 Term

Follower 收到 AppendEntries RPC:
  1. 检查 prevLogIndex 处日志是否存在且 Term 匹配
     → 若不存在或不匹配 → 返回失败 (Follower 日志落后)
     → Leader 递减 prevLogIndex 重试 (回溯匹配)

  2. 从 prevLogIndex+1 开始覆盖日志
     for each entry in Leader.entries:
       if (Follower.log[entry.index].term < entry.term):
         → 删除 Follower 本地日志 (旧 Leader 的未提交日志)
         → 写入 Leader 的日志条目
```

**为什么 Leader 的版本总是覆盖 Follower 的版本？**

因为 Leader 的 Term > Follower 的 Term（否则 Follower 不会接受 Leader 的 AppendEntries）。Raft 的安全性质保证：已提交的日志永远不会被覆盖——因为 Leader 的日志包含所有已提交的日志（Leader 选举时 Layer 1/3 检查保证新 Leader 的日志至少包含所有已提交日志）。

### 阶段 3：数据合并（Data Reconciliation）

仲裁阶段完成后，所有 Follower 的日志与 Leader 一致。Leader 推进 commitIndex → Follower 收到 Leader 的 commitIndex → State Machine 应用已提交日志 → 全集群状态一致。

**数据丢失窗口**：

分区期间旧 Leader 接受的写入（未获得多数派确认 → 未提交）将在仲裁阶段被 Leader 覆盖 → **永久丢失**。客户端需要重试这些写入——Nacos 客户端的重试机制（默认 3 次）自动重试，对客户端透明。

### Trade-off 分析

**脑裂自动恢复 vs 人工干预**：

| 维度 | 自动恢复 (JRaft 实际) | 人工干预 |
|------|----------------------|---------|
| 恢复时间 | < 500ms (检测) + < 10ms (仲裁) | 人工排查 + 手动修复（分钟~小时） |
| 数据丢失 | 未提交日志丢失 (客户端重试) | 取决于人工选择保留哪份数据 |
| 运维复杂度 | 零人工干预 | 高（需要专业人员） |
| 错误风险 | 低（协议保证安全性） | 高（人工判断可能选错数据版本） |

**未提交日志丢失 vs 客户端重试成本**：

分区期间旧 Leader 接受的未提交写入丢失，客户端重试成本：
- 配置发布：客户端 `configService.publishConfig()` 自动重试 3 次（默认），重试间隔 1s → 最多 3s 恢复
- 服务注册：客户端心跳 5s 间隔自动重新注册 → 最多 5s 恢复

### 设计模式分析

1. **版本向量模式（Version Vector）**：Raft 的 (Term, Index) 二元组构成逻辑时钟——通过比较 (Term, Index) 确定日志的新旧关系。(Term=5, Index=100) > (Term=4, Index=200) —— Term 优先于 Index（跨 Term 的比较）

2. **覆盖写模式（Overwrite Pattern）**：仲裁阶段通过 Leader 日志覆盖 Follower 日志——类似 Git 的 force push（强制推送）——以权威版本覆盖本地版本

### 小结

- Nacos 2.5.3 脑裂恢复全自动 3 阶段：(1) 检测：旧 Leader 发现新 Leader Term > 自己 → Step Down (< 500ms) (2) 仲裁：Leader AppendEntries → 日志冲突以 Leader 为准覆盖 (< 10ms) (3) 数据合并：State Machine 应用已提交日志 → 全集群一致 (< 5ms)
- 核心仲裁规则：Leader.Term > Follower.Term → Leader 日志覆盖 Follower 日志（Raft 安全性质保证）
- 数据丢失：分区期间旧 Leader 未提交写入永久丢失——客户端自动重试恢复（配置 < 3s, 服务 < 5s）
- 恢复总耗时 < 520ms（检测 500ms + 仲裁 10ms + 合并 5ms）——全自动零人工干预

## 11.6 异地三中心多活架构：同城灾备 + 异地灾备 + MySQL 半同步复制

### 设计背景

第 10.8 节讨论了基于 GeoDNS + MySQL 异步复制的多数据中心双活架构。该架构依赖 MySQL 异步复制实现跨数据中心数据同步，但异步复制的 Slave 延迟（通常 < 1s）在网络抖动或 Slave 高负载下可能扩大到秒级甚至分钟级——此时华南/华北 Nacos 集群可能读到过期配置，影响配置发布的实时性。

对于金融级、电信级等对配置一致性要求极高的关键业务，异步复制的最终一致性窗口不够。需要 MySQL **半同步复制（Semi-Synchronous Replication）**——Master 提交事务后等待至少 丛 Slave ACK 后才返回客户端成功——确保至少一个 Slave 已接收 Binlog，降低数据丢失风险。

本节提出基于 MySQL 半同步复制的**异地三中心多活架构**：同城灾备（主备中心）+ 异地灾备（第三中心），实现 RPO ≈ 0（半同步复制保证至少 1 个 Slave 实时同步）。

### MySQL 半同步复制配置

#### Master 配置（中心 A）

```ini
# /etc/mysql/mysql.conf.d/mysqld.cnf (Master - 中心 A)
[mysqld]
server-id = 1
log_bin = /var/lib/mysql/mysql-bin.log
binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON

# =========================================================================
# 半同步复制配置
# =========================================================================
# 安装半同步插件
# INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';

# 启用半同步 Master
rpl_semi_sync_master_enabled = 1

# Master 等待 Slave ACK 的超时时间（毫秒）
# 默认 10000ms (10s) → 推荐 1000ms (跨同城 RTT ~1ms + 余量)
rpl_semi_sync_master_timeout = 1000

# 等待至少 1 个 Slave ACK
rpl_semi_sync_master_wait_for_slave_count = 1
```

#### Slave 配置（中心 B - 同城灾备）

```ini
# /etc/mysql/mysql.conf.d/mysqld.cnf (Slave - 中心 B)
[mysqld]

relay_log = /var/lib/mysql/mysql-relay-bin.log
read_only = ON
super_read_only = ON
gtid_mode = ON
enforce_gtid_consistency = ON

# =========================================================================
# 半同步复制配置
# =========================================================================
# 安装半同步插件
# INSTALL PLUGIN rpl_semi_sync_slave SONAME 'semisync_slave.so';

# 启用半同步 Slave

```

#### Slave 配置（中心 C - 异地灾备）

中心 C 使用标准异步复制（无需启用半同步插件），配置同标准 MySQL Slave。

#### 建立半同步复制

```sql
-- 在 Master（中心 A）上创建复制用户
CREATE USER 'repl'@'%' IDENTIFIED BY 'Repl@2025';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
FLUSH PRIVILEGES;

-- 在 Slave B（同城）上配置半同步复制
STOP SLAVE;
CHANGE MASTER TO
  MASTER_HOST='192.168.1.100',     -- 中心 A MySQL Master
  MASTER_USER='repl',
  MASTER_PASSWORD='Repl@2025',
  MASTER_AUTO_POSITION=1;          -- GTID 自动定位
START SLAVE;

-- 验证半同步复制状态
SHOW STATUS LIKE 'Rpl_semi_sync_master_clients';
-- 预期：Rpl_semi_sync_master_clients = 1 (至少 1 个 Slave 启用了半同步)
```

### 半同步复制 vs 异步复制对比

| 维度 | 异步复制 | 半同步复制 |
|------|---------|-----------|
| **Master 提交等待** | 不等待 Slave ACK | 等待至少 1 个 Slave ACK |
| **写入延迟** | 本地提交 ( < 1ms) | + 1 RTT (同城 ~1ms, 异地 ~30ms) |
| **RPO (Recovery Point Objective)** | Seconds_Behind_Master (秒级) | ≈ 0 (至少 1 个 Slave 实时同步) |
| **Slave 宕机影响** | 不影响 Master 写入 | Master 写入降级为异步 (超时后继续) |
| **网络延迟容忍** | 高 (跨异地 ~30ms 不影响) | 中 (跨同城 ~1ms 可接受) |
| **适用场景** | 普通业务（第 10.8 节） | 金融级/电信级关键业务 |

### 故障切换流程

#### 场景 1：中心 A（主中心）故障

```
1. 检测: GeoDNS 健康检查发现中心 A Nginx VIP 不可达 (连续 3 次失败)
2. 切换: GeoDNS 自动将 DNS 解析切换到中心 B VIP
3. 数据库: 中心 B Slave 提升为 Master
   STOP SLAVE;
   RESET SLAVE ALL;
   SET GLOBAL read_only = OFF;
   SET GLOBAL super_read_only = OFF;
4. Nacos: 中心 B Nacos 集群接管所有流量
5. 恢复时间: < 30s (GeoDNS TTL=60s, TTL 过期后客户端解析到新 VIP)
```

#### 场景 2：中心 A+B（同城双中心）同时故障

```
1. 检测: GeoDNS 发现中心 A+B VIP 均不可达
2. 切换: GeoDNS 自动切换到中心 C VIP
3. 数据库: 中心 C Slave 提升为 Master (可能有 < 1s 异步复制延迟)
4. Nacos: 中心 C Nacos 集群接管所有流量 (配置数据可能滞后 < 1s)
5. 恢复时间: < 5min (跨异地切换, DNS TTL 60s + 数据库切换)
```

### Trade-off 分析

**三中心 vs 双中心**：

| 维度 | 双中心（第 10.8 节） | 三中心（本节） |
|------|---------------------|---------------|
| **同城灾备** | 无（仅 2 中心） | ✅ 中心 B 同城半同步 |
| **异地灾备** | ✅ 中心 B 异步 | ✅ 中心 C 异步 |
| **RPO (同城灾备)** | N/A | ≈ 0 (半同步实时同步) |
| **RTO** | 分钟级 (GeoDNS) | < 30s (同城切换) |
| **基础设施成本** | 2 套 Nacos + 2 MySQL | 3 套 Nacos + 3 MySQL (+50%) |
| **MySQL 写入延迟** | 异步 (本地 < 1ms) | 半同步 (+1 RTT ~1ms) |

### 设计模式分析

1. **主备模式（Active-Standby）**：中心 A 为 Active Master，中心 B 为同城 Standby（半同步实时同步）——Master 故障时 Standby 立即接管（RPO ≈ 0）。中心 C 为异地灾备（异步）——同城双中心同时故障时才接管

2. **降级模式（Degradation Pattern）**：半同步复制在 Slave 宕机或网络超时时自动降级为异步复制（`rpl_semi_sync_master_timeout=1000ms` 超时后继续提交）——避免 Slave 故障阻塞 Master 写入

### 小结

- 异地三中心多活架构：中心 A（主）+ 中心 B（同城半同步）+ 中心 C（异地异步）——三层递进灾备
- MySQL 半同步复制：Master 等待至少 1 个 Slave ACK 后才返回客户端成功 → RPO ≈ 0（至少 1 个 Slave 实时同步）
- 半同步写入延迟：同城 +1ms（1 RTT），异步 < 1ms（本地提交）——金融级业务可接受
- 故障切换：同城切换 < 30s（半同步实时同步），异地切换 < 5min（异步可能有 < 1s 延迟）
- 降级保护：Slave 宕机或超时 → 半同步自动降级为异步 → Master 写入不阻塞

## 11.7 流量切换策略：单节点故障 <30s / 中心A故障 <5min / 双中心故障 <10min

### 设计背景

Nacos 集群的高可用不仅依赖 Raft 协议的自动故障转移，还需要外层流量调度层在节点宕机、数据中心故障等场景下快速将客户端流量切换到健康节点或备用数据中心。第 10.8 节讨论了 GeoDNS 的基本解析策略，本节细化各故障场景的具体切换时间目标和操作流程。

流量切换涉及三个层级：**单节点级（Nginx upstream 摘除）、集群级（GeoDNS 切换 VIP）、数据中心级（GeoDNS 跨 DC 切换）**。每一层的切换时间目标不同，取决于健康检查间隔、DNS TTL 和故障检测延迟。

### 核心切换时间矩阵

| 故障场景 | 切换层级 | 检测方式 | 切换动作 | 目标时间 | 实际耗时分析 |
|---------|---------|---------|---------|:---:|------|
| **单节点宕机** | Nginx upstream | Nginx passive health check (max_fails=3, fail_timeout=30s) | 自动摘除故障节点 | < 30s | 连续 3 次请求失败 → 标记 DOWN → 30s 冷却期后探测恢复 |
| **单节点宕机 (gRPC)** | Nginx stream | TCP proxy_connect_timeout (5s) + fail_timeout=30s | 自动摘除故障节点 | < 35s | 5s 连接超时 × 3 次 + 30s 冷却期 |
| **集群多数派宕机** | Raft 协议 | Leader 心跳超时 (500ms) + Election Timeout (150ms) | 自动选举新 Leader | < 1s | Raft 选举 < 650ms + 日志同步 |
| **中心 A (主 DC) 故障** | GeoDNS | HTTP 健康检查 (10s 间隔, 3 次失败=30s) | DNS 解析切换到中心 B VIP | < 5min | GeoDNS TTL=60s × 3 次失败 (30s) + DNS TTL 过期 (60s) + 客户端 DNS 缓存刷新 |
| **中心 A+B (双中心) 故障** | GeoDNS | 同上 + 中心 C 冷备提升 | DNS 解析切换到中心 C VIP + MySQL Slave 提升为 Master | < 10min | 同上 + 中心 C MySQL Slave 提升为 Master (~1min) + Nacos 集群验证 (~1min) |

### 单节点故障切换流程

```
┌──────────────────────────────────────────────────────────────────────────────┐
│              单节点宕机流量切换完整时序 (HTTP 8848)                        │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  T0: Node1 (192.168.1.101:8848) 宕机                                   │
│                                                                          │
│  T0+1s: 客户端请求到达 Nginx                                           │
│         Nginx 按 least_conn 选择 Node1                                     │
│         → proxy_pass http://192.168.1.101:8848                          │
│         → 连接超时 (proxy_connect_timeout=5s)                            │
│         → 记录失败 (max_fails 计数 +1)                                   │
│                                                                          │
│  T0+1s: proxy_next_upstream → 尝试下一个节点 (Node2)                    │
│         → Node2 正常响应 → 返回客户端成功                                │

│   推荐生产调小为 5s)                                                    │
│                                                                          │
│            图 11-7：Nginx 单节点宕机被动健康检查完整时序                   │
```

### 中心级故障切换流程

**场景：中心 A（华东）整体故障（Nacos 集群 + MySQL Master 均不可达）**

```
T0: 中心 A 整体断电/网络中断
  → GeoDNS 开始健康检查失败计数

T0+10s: GeoDNS 第 1 次健康检查失败
  GET http://中心A-Nginx-VIP:8848/nacos/v1/console/server/state → 超时

T0+20s: GeoDNS 第 2 次健康检查失败
T0+30s: GeoDNS 第 3 次健康检查失败 → 触发故障切换

T0+30s: GeoDNS 自动修改 DNS 记录:
  nacos.example.com → 中心 B Nginx VIP (原 → 中心 A Nginx VIP)

T0+30s ~ T0+90s: DNS TTL 60s 过期
  → 客户端 DNS 缓存刷新 → 解析到中心 B VIP
  → 客户端连接到中心 B Nacos 集群

T0+30s ~ T0+90s: 中心 B MySQL Slave 提升为 Master:
  STOP SLAVE;
  RESET SLAVE ALL;
  SET GLOBAL read_only = OFF;
  SET GLOBAL super_read_only = OFF;

T0+90s: 中心 B 完全接管所有流量 ✅

总切换耗时: ~90s (30s 健康检查 + 60s DNS TTL)
```

### Trade-off 分析

**DNS TTL 的权衡**：

| DNS TTL | 故障切换速度 | DNS 查询压力 | 适用场景 |
|---------|:---:|---------|---------|
| 30s | 快 (< 60s) | 较高 (2× 查询频率) | 关键业务 (金融级) |
| 60s (推荐) | 中等 (~90s) | 标准 | 大多数业务 |
| 300s | 慢 (~330s) | 较低 (1/5 查询频率) | 非关键业务 |

### 设计模式分析

1. **健康检查探针模式（Health Check Probe）**：GeoDNS + Nginx 两层健康检查构成级联探针——GeoDNS 探测 Nginx VIP，Nginx 探测后端 Nacos 节点。任一层探针失败触发对应层级的故障切换

2. **断路器模式（Circuit Breaker）**：Nginx 的 `max_fails + fail_timeout` 构成标准的断路器——阈值内连续失败 → 熔断（标记 DOWN）→ 冷却期后自动探测恢复（Half-Open → Closed）

### 小结

- 三层流量切换：单节点 < 30s（Nginx passive health check）、集群级 < 1s（Raft 自动选举）、数据中心级 < 5min（GeoDNS + DNS TTL 60s）
- Nginx 单节点切换耗时 ≈ 11s（3 次请求失败 × 5s 连接超时）——推荐 `proxy_connect_timeout=5s`
- GeoDNS 切换瓶颈在 DNS TTL（60s）——TTL 过期前客户端仍解析到旧 VIP
- 双中心同时故障需提升异地 MySQL Slave 为 Master（~1min）→ 总切换 < 10min

## 11.8 MySQL 半同步复制配置：rpl_semi_sync_master + slave 完整 SQL

### 设计背景

MySQL 半同步复制是 Nacos 高可用架构的核心数据同步机制——确保至少 1 个 Slave 实时接收到 Master 的 Binlog，实现 RPO ≈ 0。第 11.6 节提出了基于半同步复制的三中心架构，本节深入 MySQL 半同步复制的完整配置、监控和故障处理。

MySQL 半同步复制的核心工作原理：

1. Master 提交事务 → 写入 Binlog → 等待至少 1 个 Slave ACK
2. Slave I/O 线程接收 Binlog → 写入 Relay Log → 返回 ACK 给 Master
3. Master 收到 ACK → 返回客户端提交成功
4. Slave SQL 线程读取 Relay Log → 应用到数据库

如果等待 Slave ACK 超时（`rpl_semi_sync_master_timeout`），Master 自动降级为异步复制——避免 Slave 故障阻塞 Master 写入。

### 完整配置 SQL

#### Phase 1：Master（中心 A）配置

```sql
-- =========================================================================
-- Master 半同步复制完整配置
-- =========================================================================

-- 1. 安装半同步 Master 插件
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';

-- 2. 启用半同步 Master
SET GLOBAL rpl_semi_sync_master_enabled = 1;

-- 3. 配置等待 Slave ACK 超时（毫秒）
-- 默认 10000ms (10s) → 推荐 1000ms (同城 RTT ~1ms + 余量)
SET GLOBAL rpl_semi_sync_master_timeout = 1000;

-- 4. 等待至少 1 个 Slave ACK
SET GLOBAL rpl_semi_sync_master_wait_for_slave_count = 1;

-- 5. 持久化配置到 my.cnf
-- 编辑 /etc/mysql/mysql.conf.d/mysqld.cnf:
-- [mysqld]
-- rpl_semi_sync_master_enabled = 1
-- rpl_semi_sync_master_timeout = 1000
-- rpl_semi_sync_master_wait_for_slave_count =  المجره
```

#### Phase 2：Slave（中心 B - 同城灾备）配置

```sql
-- =========================================================================
-- Slave 半同步复制完整配置
-- =========================================================================

-- 1. 安装半同步 Slave 插件
INSTALL PLUGIN rpl_semi_sync_slave SONAME 'semisync_slave.so';

-- 2. 启用半同步 Slave
SET GLOBAL rpl_semi_sync_slave_enabled = 1;

-- 3. 持久化配置到 my.cnf
-- [mysqld]
-- rpl_semi_sync_slave_enabled = 1
```

#### Phase 3：建立半同步复制

```sql
-- =========================================================================
-- 在 Master 上创建复制用户
-- =========================================================================
CREATE USER 'repl'@'%' IDENTIFIED BY 'Repl@2025';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
FLUSH PRIVILEGES;

-- 查看 Master Binlog 位置
SHOW MASTER STATUS;
-- 记录 File: mysql-bin.000001, Position: 1234

-- =========================================================================
-- 在 Slave B（中心 B）上配置复制
-- =========================================================================
STOP SLAVE;
CHANGE MASTER TO
  MASTER_HOST='192.168.1.100',          -- 中心 A MySQL Master IP
  MASTER_USER='repl',
  MASTER_PASSWORD='Repl@2025',
  MASTER_LOG_FILE='mysql-bin.000001',   -- 从 SHOW MASTER STATUS 获取
  MASTER_LOG_POS=1234,
  MASTER_AUTO_POSITION=1;               -- GTID 自动定位 (推荐)
START SLAVE;

-- 验证复制状态
SHOW SLAVE STATUS\G
-- 关键字段:
--   Slave_IO_Running: Yes            -- I/O 线程运行
--   Slave_SQL_Running: Yes           -- SQL 线程运行
--   Seconds_Behind_Master: 0         -- 同步延迟 (秒)
```

#### Phase 4：验证半同步复制状态

```sql
-- =========================================================================
-- Master 端验证
-- =========================================================================

-- 1. 检查半同步 Slave 数量
SHOW STATUS LIKE 'Rpl_semi_sync_master_clients';
-- 预期: 1 (至少 1 个 Slave 启用了半同步)

-- 2. 检查半同步 Master 状态
SHOW STATUS LIKE 'Rpl_semi_sync_master_status';
-- 预期: ON

-- 3. 检查半同步 Master 等待 ACK 次数
SHOW STATUS LIKE 'Rpl_semi_sync_master_yes_tx';
-- 每次半同步成功提交 +1

-- 4. 检查半同步 Master 超时次数
SHOW STATUS LIKE 'Rpl_semi_sync_master_no_tx';
-- 每次超时降级为异步 +1 (应为 0)

-- =========================================================================
-- Slave 端验证
-- =========================================================================

-- 1. 检查半同步 Slave 状态
SHOW STATUS LIKE 'Rpl_semi_sync_slave_status';
-- 预期: ON
```

### 半同步复制监控指标

| 指标 | 查询 SQL | 说明 | 告警阈值 |
|------|---------|------|---------|
| **Slave 数量** | `SHOW STATUS LIKE 'Rpl_semi_sync_master_clients'` | 启用了半同步的 Slave 数量 | < 1 → CRITICAL |
| **半同步状态** | `SHOW STATUS LIKE 'Rpl_semi_sync_master_status'` | Master 半同步是否启用 | OFF → CRITICAL |
| **半同步成功次数** | `SHOW STATUS LIKE 'Rpl_semi_sync_master_yes_tx'` | 半同步成功提交事务数 | - (累计) |
| **半同步超时次数** | `SHOW STATUS LIKE 'Rpl_semi_sync_master_no_tx'` | 超时降级为异步的事务数 | > 0 → WARNING |
| **Slave IO 运行** | `SHOW SLAVE STATUS\G` → `Slave_IO_Running` | Slave I/O 线程状态 | No → CRITICAL |
| **Slave SQL 运行** | `SHOW SLAVE STATUS\G` → `Slave_SQL_Running` | Slave SQL 线程状态 | No → CRITICAL |
| **同步延迟** | `SHOW SLAVE STATUS\G` → `Seconds_Behind_Master` | Slave 同步延迟 (秒) | > 10s → WARNING, > 60s → CRITICAL |

### 半同步降级处理流程

**场景：Slave B（同城灾备）宕机**

```
1. Master 提交事务 → 写入 Binlog → 等待 Slave B ACK
2. Slave B 宕机 → 无法返回 ACK
3. Master 等待超时 (rpl_semi_sync_master_timeout=1000ms)
4. 超时后 Master 自动降级为异步复制:
   → rpl_semi_sync_master_status = OFF
   → 事务提交成功 (异步模式)
   → rpl_semi_sync_master_no_tx += 1

5. Slave B 恢复后:
   → Slave I/O 线程重新连接 Master
   → 自动追上 Binlog (GTID 自动定位)
   → Master 检测到 Slave B 恢复:
      → rpl_semi_sync_master_status = ON
      → 恢复半同步复制
```

### Trade-off 分析

**半同步超时 vs 写入可用性**：

| rpl_semi_sync_master_timeout | 写入延迟 (Slave 正常) | Slave 宕机降级时间 | Trade-off |
|:---:|:---:|:---:|------|
| 100ms | 极低 (同城 RTT ~1ms) | 100ms 后降级 | Slave 网络抖动可能误降级 |
| 1000ms (推荐) | 低 (同城 RTT ~1ms) | 1s 后降级 | 容忍短暂 Slave 网络抖动 |
| 10000ms (默认) | 低 | 10s 后降级 | Slave 宕机阻塞 Master 写入 10s |

### 设计模式分析

1. **超时降级模式（Timeout Degradation）**：半同步复制在 Slave 宕机/超时时自动降级为异步复制——保证 Master 写入可用性优先级高于数据一致性（RPO ≈ 0 vs Master 写入可用性）

2. **心跳-ACK 模式（Heartbeat-ACK）**：Slave I/O 线程持续接收 Binlog → 返回 ACK → Master 确认 Slave 存活。类似 Raft 的 Leader-Follower 心跳机制

### 小结

- MySQL 半同步复制配置 4 阶段：(1) Master 安装插件 + 启用 (2) Slave 安装插件 + 启用 (3) 建立复制 (4) 验证状态
- 核心参数：`rpl_semi_sync_master_timeout=1000ms`（同城 RTT ~1ms + 余量）、`rpl_semi_sync_master_wait_for_slave_count=1`
- 半同步降级保护：Slave 宕机或超时 → Master 自动降级为异步 → 保证 Master 写入可用性
- 监控告警：`Rpl_semi_sync_master_no_tx > 0` → WARNING（有超时降级发生）、`Slave_IO_Running != Yes` → CRITICAL

## 11.9 优雅停机流程：从 LB 摘除→等待连接→shutdown.sh→kill -15

### 设计背景

Nacos 节点需要停机维护（版本升级、配置变更、硬件更换等）时，直接 `kill -9` 强制终止进程会导致以下问题：

1. **客户端连接突然断开**：gRPC 双向流连接突然中断——客户端感知连接断开 → 触发重连 → 可能短暂服务发现中断
2. **JRaft 日志未刷盘**：JRaft 的 Raft Log 可能尚未刷盘——宕机重启后日志丢失 → 需要从 Leader 重新同步日志
3. **Distro 异步同步任务中断**：Naming 模块的 Distro 异步同步任务尚未完成——临时实例注册信息丢失
4. **MySQL 连接池未关闭**：HikariCP 连接池未正常关闭 → MySQL 上残留 ESTABLISHED 连接 → 等待 TCP KeepAlive 超时

Nacos 2.5.3 提供了 `shutdown.sh` 脚本实现优雅停机。流程分为 4 个步骤：**从 LB 摘除 → 等待现有连接完成 → shutdown.sh → kill -15（SIGTERM）**。

### shutdown.sh 详解

Nacos 的 `shutdown.sh` 脚本位于 `${NACOS_HOME}/bin/shutdown.sh`。核心关闭逻辑：

```
1. 发送 SIGTERM 给 Nacos 进程 (kill -15 <pid>)
2. 等待 Nacos JVM 进程退出 (默认等待 30s)
3. 若超时 → 强制 kill -9
```

Nacos JVM 注册了 Shutdown Hook (`Runtime.getRuntime().addShutdownHook`)，在收到 SIGTERM 后按序执行：

```java
// NacosShutdownHook.java (简化)
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    // 1. 关闭 gRPC Server
    grpcServer.shutdown();
    
    // 2. 关闭 HTTP Server
    httpServer.shutdown();
    
    // 3. 关闭 JRaft Node
    raftNode.shutdown();
    
    // 4. 关闭 MySQL 连接池
    dataSource.close();
    
    // 5. 刷盘 Raft Log
    raftLog.flush();
    
    // 6. 等待 Distro 同步任务完成
    distroTaskManager.awaitTermination(5, TimeUnit.SECONDS);
}));
```

### 完整优雅停机脚本

```bash
#!/bin/bash
# graceful-shutdown.sh - Nacos 节点优雅停机脚本

NACOS_HOME="/opt/nacos"
NACOS_IP="192.168.1.101"           # 当前节点 IP
NGINX_CONF="/etc/nginx/conf.d/nacos-http.conf"
NGINX_STREAM_CONF="/etc/nginx/conf.d/nacos-grpc.conf"

echo "============================================================"
echo "  Nacos 节点优雅停机开始: $(date)"
echo "  Node: ${NACOS_IP}"
echo "============================================================"

# =========================================================================
# Step 1: 从 LB 摘除
# =========================================================================
echo "[Step 1] 从 Nginx upstream 摘除节点..."

# HTTP upstream (8848)
sed -i "s/server ${NACOS_IP}:8848;/server ${NACOS_IP}:8848 down;/" ${NGINX_CONF}
# gRPC stream upstream (9848)
sed -i "s/server ${NACOS_IP}:9848;/server ${NACOS_IP}:9848 down;/" ${NGINX_STREAM_CONF}

nginx -s reload
echo "Nginx reloaded → 新连接不再路由到 ${NACOS_IP}"

# 等待 Nginx 健康检查生效
sleep 5

# =========================================================================
# Step 2: 等待现有连接完成
# =========================================================================
echo "[Step 2] 等待现有连接自然关闭..."

# 检查 HTTP 连接数
CONN_COUNT=$(ss -tnp | grep ":8848" | grep ESTABLISHED | wc -l)
echo "当前 HTTP 连接数: ${CONN_COUNT}"

# 等待 gRPC 连接关闭 (最长等待 120s = proxy_timeout)
echo "等待 gRPC 连接自然关闭 (最长 120s)..."
sleep 10

# 检查 Distro 同步任务
echo "检查 Nacos 状态..."
curl -s http://localhost:8848/nacos/v1/console/server/state

# =========================================================================
# Step 3: 执行 shutdown.sh
# =========================================================================
echo "[Step 3] 执行 shutdown.sh..."
cd ${NACOS_HOME}/bin
bash shutdown.sh

# =========================================================================
# Step 4: 等待进程退出
# =========================================================================
echo "[Step 4] 等待 Nacos 进程退出 (最多 30s)..."

for i in $(seq 1 30); do
    if ! pgrep -f nacos > /dev/null; then
        echo "Nacos 进程已正常退出"
        break
    fi
    sleep 1
done

# 超时 → SIGKILL
if pgrep -f nacos > /dev/null; then
    echo "超时 30s → 发送 SIGKILL"
    kill -9 $(pgrep -f nacos)
    sleep 反映了
    echo "Nacos 进程已强制终止"
fi

echo "============================================================"
echo "  Nacos 节点优雅停机完成: $(date)"
echo "============================================================"
```

### Trade-off 分析

**优雅停机 vs 强制终止**：

| 维度 | 优雅停机 (shutdown.sh) | 强制终止 (kill -9) |
|------|----------------------|-------------------|
| 客户端感知 | 连接自然关闭 → 客户端无感重连 | 连接突然断开 → 客户端感知错误 |
| JRaft 日志安全 | 刷盘后再关闭 | 未刷盘日志丢失 |
| MySQL 连接池 | 正常关闭 + 释放连接 | 残留 ESTABLISHED → 等待 TCP KeepAlive |
| 停机耗时 | ~30-120s (等待连接关闭) | < 1s |
| 适用场景 | 计划内停机 (版本升级/维护) | 紧急故障 (进程卡死) |

### 设计模式分析

1. **优雅关闭模式（Graceful Shutdown）**：4 步骤逐步关闭——从 LB 摘除 → 等待连接 → shutdown.sh → kill -15。每一步逐步缩小服务范围，确保客户端无感

2. **超时-强制模式（Timeout-Force）**：等待 30s 超时 → SIGKILL 强制终止——避免进程卡死无限等待。类似 Go 的 `context.WithTimeout` 模式

### 小结

- Nacos 优雅停机 4 步骤：(1) 从 LB 摘除 → (2) 等待现有连接完成 → (3) shutdown.sh → (4) kill -15 (最后手段)
- LB 摘除：Nginx upstream 标记节点 `down` + reload → 新连接不路由到该节点
- shutdown.sh 内部按序关闭：gRPC → HTTP → JRaft → MySQL → Distro → Raft Log 刷盘
- 等待连接关闭：HTTP < 5s，gRPC < 120s (proxy_timeout)
- kill -9 仅作为最后手段——SIGKILL 不留任何清理机会（JRaft 日志可能丢失）

## 11.10 滚动重启流程：逐个节点摘除→停机→启动→验证→恢复 LB

### 设计背景

Nacos 集群版本升级、配置变更或安全补丁需要重启集群节点。但直接重启所有节点会导致集群不可用——所有 gRPC 长连接断开、服务发现中断。因此必须采用**滚动重启（Rolling Restart）**：逐个节点重启，每次只重启 1 个节点，保持集群 quorum 可用。

Nacos 2.5.3 集群的滚动重启需要考虑以下特殊因素：

1. **JRaft 选举影响**：重启 Follower 节点不影响集群——Leader 仍正常。但重启 Leader 节点会触发 Leader 选举——短暂期间（< 1s）集群不接受写入
2. **Distro 异步同步中断**：重启节点上的 Distro 异步同步任务中断——临时实例注册信息在重启期间无法同步到该节点。但 Naming 模块的 Distro 通过 Checksum 校验恢复后自动追平
3. **gRPC 连接迁移**：重启节点上的 gRPC 连接断开——客户端自动重连到其他节点。gRPC 客户端内置重连机制（默认 3 次重试，间隔 1s）
4. **MySQL 连接池重启**：重启后 HikariCP 连接池重新建立 MySQL 连接——短暂期间（< 1s）该节点无法读写 MySQL

### Leader 重启的特殊处理

重启 Leader 节点与重启 Follower 节点有本质区别——Leader 重启会触发 Raft Leader 选举，短暂期间（< 1s）集群不接受写入。推荐**先主动退位再重启**：

**对比：主动退位 vs 直接重启 Leader**：

| 维度 | 主动退位 (推荐) | 直接重启 Leader |
|------|----------------|---------------|
| **Leader 选举耗时** | < 1s (预先选举) | ~15s (等待心跳超时 + 选举) |
| **写入中断时间** | < 1s (选举期间) | ~15s (心跳超时 + 选举) |
| **客户端感知** | 无感 (gRPC 自动重连到新 Leader) | ~15s 写入失败 (Leader 不可达) |
| **Raft 日志安全** | Leader 主动刷盘后退位 → 日志完整 | Leader 突然宕机 → 未刷盘日志可能丢失 |

**主动退位 API**：

```bash
# 通过 JRaft HTTP API 触发 Leader Step Down
curl -X POST http://192.168.1.101:7848/jraft/stepDown
# 预期响应: {"status":"OK","newLeader":"192.168.1.102:7848"}
```

### 完整滚动重启脚本

```bash
#!/bin/bash
# rolling-restart.sh - Nacos 集群滚动重启脚本

NACOS_HOME="/opt/nacos"
NODES=("192.168.1.101" "192.168.1.102" "192.168.1.103")
NGINX_CONF="/etc/nginx/conf.d/nacos-http.conf"
NGINX_STREAM_CONF="/etc/nginx/conf.d/nacos-grpc.conf"

echo "============================================================"
echo "  Nacos 集群滚动重启开始: $(date)"
echo "============================================================"

for NODE_IP in "${NODES[@]}"; do
    echo "------------------------------------------------------"
    echo "  Round: 重启节点 ${NODE_IP}"
    echo "------------------------------------------------------"
    
    # =====================================================================
    # Phase 0: 检查是否为 Leader → 主动退位
    # =====================================================================
    LEADER_CHECK=$(curl -s http://${NODE_IP}:8848/nacos/v1/core/cluster/nodes | \
        python3 -c "import sys,json; nodes=json.load(sys.stdin); \
        leader=[n['ip'] for n in nodes if n.get('extendInfo',{}).get('role')=='LEADER']; \
        print(leader[0] if leader else '')" 2>/dev/null)
    
    if [ "${LEADER_CHECK}" = "${NODE_IP}" ]; then
        echo "[Phase 0] ${NODE_IP} 是 Leader → 主动退位..."
        curl -X POST http://${NODE_IP}:7848/jraft/stepDown
        sleep 2
        echo "Leader 已退位 → 新 Leader 已选举"
    fi
    
    # =====================================================================
    # Phase 1: 从 LB 摘除
    # =====================================================================
    echo "[Phase 1] 从 Nginx 摘除 ${NODE_IP}..."
    ssh ${NODE_IP} "sed -i 's/server ${NODE_IP}:8848;/server ${NODE_IP}:8848 down;/' ${NGINX_CONF}"
    ssh ${NODE_IP} "sed -i 's/server ${NODE_IP}:9848;/server ${NODE_IP}:9848 down;/' ${NGINX_STREAM_CONF}"
    nginx -s reload
    sleep 5
    
    # =====================================================================
    # Phase 2: 优雅停机
    # =====================================================================
    echo "[Phase 2] 优雅停机 ${NODE_IP}..."
    ssh ${NODE_IP} "cd ${NACOS_HOME}/bin && bash shutdown.sh"
    sleep 燤
    
    # =====================================================================
    # Phase 3: 启动
    # =====================================================================
    echo "[Phase 3] 启动 ${NODE_IP}..."
    ssh ${NODE_IP} "cd ${NACOS_HOME}/bin && bash startup.sh"
    
    # 等待 Nacos 完全启动 (JRaft 选举 + MySQL 连接)
    echo "等待 ${NODE_IP} 完全启动 (最长 60s)..."
    for i in $(seq 1 60); do
        HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" http://${NODE_IP}:8848/nacos/v1/console/server/state 2>/dev/null)
        if [ "${HTTP_CODE}" = "200" ]; then
            echo "${NODE_IP} 已启动 (${i}s)"
            break
        fi
        sleep 1
    done
    
    # =====================================================================
    # Phase 4: 验证
    # =====================================================================
    echo "[Phase 4] 验证 ${NODE_IP} 集群状态..."
    curl -s http://${NODE_IP}:8848/nacos/v1/core/cluster/nodes | python3 -m json.tool
    
    # =====================================================================
    # Phase 5: 恢复 LB
    # =====================================================================
    echo "[Phase 5] 恢复 ${NODE_IP} 到 LB..."
    ssh ${NODE_IP} "sed -i 's/server ${NODE_IP}:8848 down;/server ${NODE_IP}:8848;/' ${NGINX_CONF}"
    ssh ${NODE_IP} "sed -i 's/server ${NODE_IP}:9848 down;/server ${NODE_IP}:9848;/' ${NGINX_STREAM_CONF}"
    nginx -s reload
    
    echo "Round 完成: ${NODE_IP} ✅"
done

echo "============================================================"
echo "  Nacos 集群滚动重启完成: $(date)"
echo "============================================================"
```

### Trade-off 分析

**滚动重启 vs 全集群同时重启**：

| 维度 | 滚动重启 (推荐) | 全集群同时重启 |
|------|----------------|---------------|
| 集群可用性 | 始终保持 quorum 可用 | 全集群不可用 |
| 客户端感知 | 无感 (gRPC 自动重连到其他节点) | 全集群连接断开 |
| 重启总耗时 | N × (停机+启动) 时间 (串行) | max(停机+启动) 时间 (并行) |
| 风险 | 低 (始终保持 quorum) | 高 (全集群不可用) |
| 适用场景 | 生产环境 (唯一选择) | 开发/测试环境 |

### 设计模式分析

1. **滚动更新模式（Rolling Update）**：逐个节点重启——类似 K8s StatefulSet 的 `RollingUpdate` 策略——每次只更新 1 个 Pod，保持集群 quorum 可用

2. **主动退位模式（Voluntary Stepdown）**：Leader 主动退位而非直接重启——避免 Leader 突然宕机导致的 Raft 选举延迟（心跳超时 15s vs 主动退位 < 1s）

### 小结

- Nacos 集群滚动重启 5 阶段：(1) 从 LB 摘除 → (2) 优雅停机 → (3) 启动 → (4) 验证集群状态 → (5) 恢复 LB
- Leader 重启特殊处理：先通过 JRaft API 主动退位（`/jraft/stepDown`）→ 选举新 Leader < 1s → 再重启旧 Leader
- 滚动重启始终保持集群 quorum 可用——3 节点集群每次只重启 1 节点，仍有 2/3 多数派在线
- 全流程脚本自动化——逐个节点执行 5 阶段，无需人工介入
